# 탭 카운터 `counter-tap`  ·  counter

**Verdict:** needs-fix  ·  **Mode:** single

## 주제 매력도
현재 주제("그냥 숫자 세기")는 매력이 약하다. 순수 카운터는 도구일 뿐 휘발성 스낵의 "재미 한 순간"이 없다. 더 매력적인 방향: (1) 10초 안에 몇 번 탭하나 — "탭 스피드 테스트"로 리프레이밍(시간 제한 + 점수 + 등급). 사람들이 좋아하는 검증된 포맷이며, 끝나면 "당신은 84탭/10초 = 상위 12%" 같은 즉시 결과/공유 훅이 생긴다. (2) 또는 "참을 수 있나? 한 번만 더 누르고 싶은" 클리커. 둘 다 현재의 무한 카운터보다 시작-끝-결과가 있어 스낵에 맞는다. 권장: 탭 스피드 테스트로 전환.

## 레퍼런스 (검증된 인기 포맷 모방)
- **모방 대상:** 탭 스피드 테스트 / Kohi Click Test (CPS Test, 초당 클릭수 테스트)
- **구조 100% 복제:** 검증된 CPS 테스트 룰을 100% 모방: (1) 시작 화면 → 첫 탭 순간 타이머(10초 또는 5초) 시작, (2) 제한 시간 동안 큰 버튼 연타, (3) 매 탭 카운트+1 즉시 피드백(숫자 펑/햅틱), (4) 0초가 되면 입력 잠금 → 결과 화면(총 탭수, 초당 클릭수 CPS, 등급/백분위), (5) '다시하기'로 즉시 리플레이. 진행바/카운트다운이 데드타임을 없앤다.
- **우리 콘텐츠/디자인:** 콘텐츠=KR 톤 등급 카피('손가락 광속 🏎️', '거북이 모드 🐢', '평범한 인간' 등)와 CPS 구간별 멘트, 백분위 문구. 디자인=블랙(#0b0c0e)+라임(#d9ff00) 그대로, 큰 라임 탭 버튼은 좋은 자산이라 유지. 결과 화면도 같은 톤으로 새로 디자인.

## 목적
소비자가 잠깐 손가락 속도를 시험하고 "내가 몇 탭/초인지" 즉석 점수를 받아 친구에게 자랑/공유하는 휘발성 스낵. 현재 구현은 시작도 끝도 없는 무한 카운터라 "한 순간의 재미"가 없다 — 도구에 가깝다.

## 핵심 루프
큰 라임 버튼을 제한 시간 동안 최대한 빠르게 연타 → 카운트가 즉시 오르고 타이머가 줄어듦 → 0초에 점수/등급 결과 → 다시하기. (현재 구현: 무한히 +1만 하는 단순 증가 루프.)

## 시나리오
1. 사용자가 앱을 열면 큰 라임 탭 버튼과 '현재 기록 0', '대기' 상태가 보인다
2. 사용자가 라임 버튼을 탭한다 → 큰 숫자가 0→1로 즉시 바뀐다 (countText 바인딩 동작 확인됨)
3. 사용자가 연속으로 탭한다 → 숫자가 1→2→3 매번 즉시 반응한다
4. 사용자가 하단 '누적'/'상태' 카드를 본다 → (의도) 누적 횟수와 '기록 중' 상태가 갱신되어야 하나 현재 0회/대기에 멈춰 있다 (결함)
5. 사용자가 '리셋하기'를 탭한다 → 카운트가 0으로, lastAction이 '리셋했어요'로 바뀐다
6. (권장 리팩터 후) 첫 탭에 타이머 시작 → 10초 후 입력 잠금 → CPS/등급 결과 표시 → '다시하기'로 재시작

## 성공 기준
- 탭 버튼이 모든 탭에 0 데드타임으로 즉시 반응한다(snappy)
- 큰 카운트 숫자가 탭마다 정확히 +1 갱신된다
- 하단 통계 카드(누적/상태)가 실제 카운트와 일치한다 — 멈춰 있으면 실패
- lastAction 문구가 실제 횟수와 일치하고(오프바이원 없음) 한 영역 안에서 깨지지 않게 들어간다
- 블랙+라임 톤 일관, 텍스트 겹침/잘림 없음
- (목표 포맷이면) 타이머·점수·등급이 보이고 끝-결과-리플레이 흐름이 있다

## QA 검증 시나리오
- [ ] **QA1** 탭 버튼(tapTarget) 클릭 시 count가 +1 되는가 → `매 탭마다 countText가 0→1→2 증가 (스샷 1,2,3에서 확인됨 — PASS)`
- [ ] **QA2** '누적' StatCard value가 count와 함께 갱신되는가 → `count=2면 '2회' 표시. 실제로는 '0회' 고정 — FAIL`
- [ ] **QA3** '상태' StatCard value가 count>0일 때 '기록 중'으로 바뀌는가 → `count=2면 '기록 중'. 실제로는 '대기' 고정 — FAIL`
- [ ] **QA4** lastAction 문구의 횟수가 실제 count와 일치하는가 → `count=1일 때 '총 1회'. 실제 '총 2회'(count+1 오프바이원) — FAIL`
- [ ] **QA5** 리셋하기 버튼이 count를 0으로, 문구를 리셋 메시지로 되돌리는가 → `클릭 시 0/리셋 메시지 (트리거 정의는 있음, 통계 카드 동일 결함 가능성)`
- [ ] **QA6** 모든 텍스트가 화면 안에 들어오고 겹치지 않는가 → `lastActionText가 좁은 폭에서 3줄로 줄바꿈돼 답답함 — 부분 FAIL`
- [ ] **QA7** 카테고리(counter) 특유: 시작/종료/결과가 있는가 → `현재 무한 증가만 있고 점수·타이머·결과 없음 — 스낵으로서 미달`

## 현재 깨짐 (진단)
- **[high]** '누적' StatCard가 count와 무관하게 '0회'에 고정됨. 컴포넌트 인스턴스 propValue 바인딩(totalStat.value: `${count}회`)이 재전파되지 않는 레거시 엔진 gotcha — 직접 텍스트 레이어 바인딩(countText)만 동작.
  - 근거: counter-tap-1/2/3.png 비교: 큰 숫자는 0→1→2로 변하는데 좌하단 '누적' 카드는 세 장 모두 '0회' 그대로. 문서 L184-187 totalStat propValues.value, L364-410 StatCard def.
  - 수정: 통계 값을 컴포넌트 propValue 바인딩 대신 직접 text 레이어(예: heroCard 내부 또는 별도 text 레이어 id)로 빼서 idle.bindings에서 직접 .content 바인딩. 또는 runtime이 propValue 재전파를 지원하도록 수정. 현 엔진 제약상 직접 텍스트 바인딩이 안전.
- **[high]** '상태' StatCard가 count>0인데도 '대기'에 고정됨. 동일한 propValue 미재전파 결함.
  - 근거: counter-tap-3.png에서 count=2인데 우하단 '상태' 카드 '대기'. 문서 L233 statusStat.value 삼항식, L195-202 statusStat 인스턴스.
  - 수정: 위와 동일 — 직접 text 레이어로 전환해 idle.bindings에서 바인딩.
- **[medium]** lastAction 문구 오프바이원: count=1일 때 '총 2회'로 표시(setVar에서 count는 이미 증가했는데 expr이 count+1 사용).
  - 근거: counter-tap-2.png(countText=1) → '방금 1회를 추가했어요 · 총 2회'. 문서 L249-252 expr `총 ${count + 1}회` — setVar count 증가 후 평가되면 +2 됨.
  - 수정: 두 setVar 실행 순서/스냅샷에 맞춰 expr을 `총 ${count}회`로 수정(count 증가 응답이 먼저 적용된다면).
- **[low]** lastActionText가 heroCard 좁은 폭(패딩 22)에서 긴 문구가 3줄로 줄바꿈돼 답답하고 카드 하단을 밀어냄.
  - 근거: counter-tap-2/3.png 하단 '방금 1회를 / 추가했어요 · 총 / 2회' 3줄 래핑.
  - 수정: 문구를 짧게('총 N회')로 줄이거나 fontSize/폭 조정, nowrap 처리.
- **[medium]** 제품 정체성 미달: 무한 카운터라 시작·종료·결과가 없어 휘발성 스낵의 '한 순간 재미'와 공유 훅이 없음.
  - 근거: states에 idle 하나뿐, 타이머/점수/결과 상태 없음. 문서 L228-275.
  - 수정: reference의 CPS 테스트 룰로 리팩터(타이머+점수+등급+리플레이).

## 멀티 변형 아이디어 (별도 앱)
멀티로 만들면 매우 재밌다: live-race(라이브 경쟁) — 같은 방의 2~N명이 동시에 10초 연타, 서버가 setVar로 각자 카운트를 실시간 동기화해 막대 레이스로 표시하고 0초에 우승자 발표. setVar 브로드캐스트(서버→전체 동기화) 훅과 잘 맞아 별도 '탭 배틀' 멀티 앱으로 고도화 가치 높음.
