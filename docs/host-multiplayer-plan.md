# 호스트 방식 멀티플레이 계획 — "호스트 권한 + 얇은 중계"

> 2026-10-07 초안 · 논의 후 진행. 게임하는 사람이 몇 명 안 되니(방당 2–8명) 게임 진행을
> 서버 대신 **방장(호스트) 기기**가 맡고, 서버는 메시지만 전달하는 구조로 바꾼다.

## 1. 왜
- 지금은 방마다 서버가 세션 타이머·집계·판정을 직접 돌린다 → 방이 늘수록 서버 CPU·메모리·운영 부담이 늘고, 서버가 죽으면 모든 방이 같이 죽는다.
- 방은 작고 휘발성이다 → 진행 권한을 참가자 기기에 줘도 된다. 서버는 "누가 같은 방인지 이어 주는 일"만 하면 된다.

## 2. 지금 서버가 하는 일 (실측, `snack-server/src/index.mjs`)
| 영역 | 내용 | 호스트로 옮김? |
|---|---|---|
| 방 연결 | 입장(hello)·참가자 수·명단(roster)·반응 이모지 | 중계가 담당(얇게) |
| 세션 진행 | lobby→countdown→play→result 타이머, 라운드(투표·퀴즈·토너먼트·눈치·반응속도), 채점 | **호스트로** |
| 방 상태 | 투표 집계(1인 1표), 협동 합계, 점수판·raceBoard | **호스트로** |
| 콘텐츠 | 라운드 콘텐츠 팩(dynamicPack) | 호스트가 `/api/content`(HTTP, 캐시 가능)로 받음 |
| 영구 데이터 | 템플릿 방 투표 결과 디스크 저장 | **결정 필요(§6-②)** |
| 전역 | 유저 포인트 순위, 활동 로그·트렌딩, "지금 N명" | 서버에 남김(가벼운 이벤트 수집) |
| API | 템플릿·앱 저장·콘텐츠·이미지·사진·AI 빌더 | 그대로(정적/HTTP) |

## 3. 설계
```
 참가자 폰 ──action──▶ 중계(방 라우터) ──▶ 호스트 폰: RoomEngine ──setVar──▶ 중계 ──▶ 모든 폰
                          │  호스트 선출·교체, 상태 스냅샷 보관, 속도 제한
```
- **RoomEngine (신규 `packages/snack-room`)**: 지금 서버의 방 로직을 **순수 모듈**로 뽑는다. 입력 = action/입장/퇴장, 출력 = setVar 브로드캐스트. 시계·타이머·전송·콘텐츠는 주입 → 같은 코드가 **서버(지금 방식)와 호스트 브라우저 양쪽**에서 돈다. Bite 앱 문서는 `emit`/`setVar` 그대로라 **수정 0**.
- **중계(relay)**: 방별 메시지 전달만. 첫 입장자 = 호스트. 호스트가 주기적으로(예: 1초, 변경 시) 상태 스냅샷을 중계에 맡긴다.
- **호스트 교체**: 호스트 연결 끊김·하트비트 2초 누락 → 다음 참가자가 호스트가 되어 마지막 스냅샷으로 이어서 진행(남은 타이머는 남은 시간으로 재설정). 호스트 탭이 백그라운드로 가면(`visibilitychange`) **스스로 넘긴다** — 모바일은 백그라운드 탭 타이머가 멈추기 때문.
- **공정성**: 반응속도·퀴즈 속도 점수는 호스트가 받은 시각 기준(중계 지연 수십 ms 포함). 캐주얼 스낵에 충분 — 호스트 조작 가능성은 감수(친구끼리 하는 방).
- **전송 추상화 (플레이어)**: `LiveApp`이 `RoomTransport` 인터페이스만 본다 — `ServerTransport`(지금) / `RelayTransport`(호스트·참가자). 플래그로 전환.
- **순수 P2P(WebRTC)는 쓰지 않는다**: 한국 모바일망은 직접 연결 실패가 잦아 결국 TURN 중계 서버(유료)가 필요 — 중계를 둘 거면 WebSocket 중계가 더 단순·안정적.

## 4. 단계
| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **H0** 방 로직 추출 | index.mjs의 방·세션 로직 → `packages/snack-room` 순수 모듈. 서버는 이 모듈을 그대로 사용 | 가짜 타이머 단위테스트 + **multiclient-sim 13/13 그대로** (동작 변화 0) |
| **H1** 전송 추상화 | 플레이어 `RoomTransport`, LiveApp 리팩터 | 오라클 44/44 그대로 |
| **H2** 중계 + 호스트 모드 | 기존 Node 서버에 `/relay`(라우팅·선출·스냅샷) + 브라우저 호스트 실행, `?host=1` 플래그 | 호스트 모드로 multiclient-sim 13/13 |
| **H3** 교체·백그라운드 | 호스트 이탈/하트비트/백그라운드 핸드오프, 늦은 입장 | 신규 시뮬: 라운드 중 호스트 퇴장 → 끊김 없이 이어짐 |
| **H4** 전역 이벤트 | 호스트가 "게임 종료·점수" 이벤트를 서버에 보냄 → 유저 포인트·트렌딩 유지 | 홈 통계 정상 |
| **H5** 중계 이전(선택) | 중계를 서버리스(예: Cloudflare Durable Objects)로 — Node 서버는 정적+API만 | 비용·지연 측정 후 결정 |

## 5. 리스크
- 호스트 폰 성능·배터리: 방 로직은 가벼움(타이머·집계) — 렌더링 대비 무시할 수준.
- 백그라운드: iOS Safari는 탭을 숨기면 타이머가 크게 느려짐 → H3 핸드오프가 필수.
- 동시 시작·이중 호스트: 선출은 중계가 단독 결정(방당 단일 진실).

## 6. 결정할 것
1. **중계 위치**: H2는 지금 Node 서버에 붙여 검증 → H5에서 서버리스 이전 여부 결정 (추천).
2. **템플릿 방 투표 영구 저장**: 지금은 공식 템플릿 방의 투표가 디스크에 쌓인다. 호스트 방식에선
   (a) 휘발성으로 바꾼다 — 스낵 정체성(휘발성)과 맞음, 서버 상태 0 (**추천**) /
   (b) 호스트가 결과만 서버에 보내 누적 — 서버에 쓰기 API가 남음.
3. **적용 범위**: 먼저 세션 게임(멀티 템플릿) + 친구 방에 적용, 공식 템플릿 공개 방은 H4 이후 (추천).
