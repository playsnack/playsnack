# PlaySnack 사업 방향과 2026 실행 계획 (2026-10-13)

> **결론:** PlaySnack은 짧은 놀이를 만들고 링크로 사람을 모아 동시에 플레이하는 **무료 소셜 놀이 플랫폼**을 지향한다. 지금 서비스 상태는 **Beta**다. 올해는 **나 맞히기 → 초대 → 동시 플레이** 한 흐름을 완성해 공개하고, 수익 모델은 실제 이용을 본 뒤 결정한다.

## 계획 문서 체계

이 문서를 **현재 계획의 입구이자 제품 방향의 원본**으로 둔다. 계획이 흩어지지 않게 아래처럼 역할을 나눈다.

| 문서/도구 | 역할 |
|---|---|
| `docs/business-plan-2026.md` | 현재 제품 방향, 올해 실행 순서, 공개 조건의 원본 |
| GitHub Project / Issues | 실제 실행 백로그. 작업은 여기서 Epic/Story/Task로 쪼개고 Done을 판단한다 |
| `docs/master-plan.md` | 2026-10-12 기준 기술 품질 백로그 아카이브. 필요한 항목만 이슈로 옮겨 최신화한다 |
| `docs/project-spec.md`, `specs/*` | 품질 기준과 기능별 스펙 참고문서. 현재 작업의 원본은 연결된 이슈/PR이다 |
| `docs/audit/*` | 근거와 관찰 기록. 바로 실행하지 않고 이슈로 전환한 뒤 작업한다 |
| `docs/native-engine-plan.md` 등 오래된 계획 | 보류/아카이브. 현재 계획을 바꾸려면 먼저 이 문서와 이슈를 갱신한다 |

원칙: 새 계획을 만들기보다 이 문서를 갱신하고, 실행할 일은 GitHub Issue로 옮긴다. 오래된 계획 문서에서 바로 브랜치를 파지 않는다.

## 현재 결정

- **배포/실행 기준:** Vercel은 제거했고 Cloudflare를 기준으로 운영한다. 계획과 문서의 Vercel 전제는 과거 기록으로 보고 최신 실행 기준으로 쓰지 않는다.
- **방 보안 방향:** 무료 베타 공개 전에는 Cloudflare Worker / Durable Objects 기반으로 방 입장을 검증한다. 선택적 PIN은 화면 장식이 아니라, Worker가 확인하고 방에 접속 가능한 짧은 권한을 발급하는 구조여야 한다.
- **대표작:** 첫 대표작은 **나 맞히기**다.
- **파생 후보:** `여기 중에 누군지 맞히기`, `우리 중 누가?`, 모임/친구 캐릭터 퀴즈는 나 맞히기에서 파생되는 후속 후보로 둔다.
- **추천작:** 실기기에서 검증했거나 수정 완료된 게임만 홈의 추천작에 올린다. 수정 중인 게임은 추천작이 아니라 추천 후보/실험작으로 둔다.

## 제품 가설

- **경험:** 한 사람이 게임을 고르고 필요한 속성만 채워 초대한다. 참가자는 로그인 없이 동시에 플레이하고, 참여자·순위 또는 결과를 함께 보고 공유한다.
- **차별점:** 실시간 퀴즈도 테마로 두되, 친구의 닉네임과 선택이 캐릭터와 결과에 반영되는 놀이를 넓힌다. AI 생성은 필수가 아니다.
- **출발점:** 단톡방과 소규모 모임은 첫 사용 환경이지 확정된 고객군이 아니다. 직접 실험을 섭외하지 못해도 무료로 공개하고 실제 사용을 본다.
- **질문:** 사람들이 한 판을 끝내고 다시 열거나, 참가했던 사람이 새 게임을 만드는가?

## 무료 베타에서 볼 숫자

- **핵심:** 주간 3명 이상이 끝낸 판 수. 결과 화면 조회가 아니라 한 판당 한 번 센다.
- **생성:** 누적 및 주간 신규 방 수와 커스텀 게임 수를 구분한다. 속성 편집을 확정해 플레이 가능한 게임만 생성으로 센다.
- **반응:** 입장 실패, 재경기, 공유와 결과 화면의 선택형 한 문항을 함께 본다. 설문 응답만으로 성공을 판단하지 않는다.
- **활성 이용자:** MAU는 최근 30일에 게임을 실제로 조작하거나 응답한 이용자로 정의한다. 지금 셀 수 있는 것은 **기기(브라우저) 수 추정**뿐이다(2026-10-14, [익명 측정](telemetry.md) §4a): 브라우저마다 무작위 번호를 두고 하루 한 번 보내면, 서버는 비밀 솔트로 해시해 HyperLogLog에만 넣는다(오차 약 1%, 번호 목록은 남지 않음). **기기 ≠ 사람** — 한 사람이 폰과 PC를 쓰면 2대, 시크릿 창·저장소 삭제면 새 기기다. 그래서 이 숫자는 "월 활성 기기(추정)"라고 부르고 MAU·유저 수라고 부르지 않는다. 방문·입장 횟수도 유저 수가 아니다.
- **자주 쓰는 기기(유료 대상 신호):** 같은 기기가 자주 쓰는지는 미래 유료 대상(모임 운영자·업체 같은 헤비 유저)을 가늠하는 신호다. 서버는 기기별로 아무것도 두지 않는다 — 각 브라우저가 자기 사용 횟수를 자기 안에만 두고, 하루 한 번 **구간**(사용한 날 수 · 끝까지 본 판 · 만든 퀴즈 · 처음 쓴 지 며칠)만 보낸다. 그래서 "10판 이상 한 기기가 몇 %"는 알 수 있어도 **그게 누구인지는 알 수 없다.** 연락·전환 같은 영업에는 쓸 수 없고, 쓸 수 있게 만들려면 동의를 받는 별도 설계가 필요하다.

## 올해 할 일: 무료 베타까지

| 순서 | 작업 | 확인할 것 |
|---|---|---|
| 1. 실시간 품질 | Cloudflare 방 구조와 링크 입장을 실기기에서 검증하고 실패를 고친다. | 3명 이상 입장 20/20, 결과 불일치 0건. |
| 2. 대표작 | **나 맞히기**에 간단한 속성 편집, 초대·대기방, 동시 플레이, 결과·재경기·공유를 완성한다. | 처음 온 사람이 도움 없이 만들고 초대해 한 판을 끝낸다. |
| 3. 측정 | 기존 익명 측정을 앱에 연결하고 방·게임 생성, 판 완료, 재경기, 공유, 선택형 반응을 집계한다. | 기술 실패와 실제 놀이·반응을 구별할 수 있다. |
| 4. 무료 공개 | 인증된 방과 선택적 PIN을 갖추고 품질을 재검증한 뒤 무료 베타를 공개한다. 알릴 채널 1~2곳을 정한다. | 섭외한 모임 수와 무관하게 누구나 로그인 없이 플레이할 수 있다. |
| 5. 주간 점검 | 신규 방·게임, 3명 이상 완료한 판, 재경기·공유·반응과 오류를 주 1회 본다. 가능할 때만 이용자에게 짧게 묻는다. | 유입이 없으면 알리는 방법, 입장이 막히면 품질, 완주가 적으면 게임 경험을 고친다. |

**이번 주 착수:** Cloudflare 방 입장 검증, 나 맞히기 대표작 polish, 판 완료·생성 지표 정의부터 시작한다.

**연말 목표:** 2026-12-31까지 첫 게임을 무료 베타로 공개하고 위 지표의 기준선을 확보한다. 임의의 유저·모임 수를 출시 조건으로 삼지 않는다. 현재 익명 집계로는 같은 그룹의 재방문이나 참가자→개설 전환을 알 수 없으므로, 관찰 또는 개인정보 보호 설계가 마련되기 전까지 단정하지 않는다.

## 범위와 공개 조건

- 여러 장르를 동시에 만들지 않는다. 퀴즈와 캐릭터 참여형 게임은 방향에 맞지만 대표작은 나 맞히기로 고정한다. 셀카 캐릭터는 사진 없이도 입장할 수 있는 후속 재미 요소다.
- 가입, 사진·실명 입력, 범용 AI 제작 도구는 첫 무료 베타의 조건이 아니다. 수익화도 올해의 성공 기준으로 삼지 않는다.

현재 공개 MQTT 방은 비공개 방이 아니며 화면용 PIN만으로는 보호되지 않는다. 불특정 다수에게 공개하기 전에는 Cloudflare Worker / Durable Objects 기반의 인증된 방과 품질 게이트를 갖춘다.

연말에는 실제 사용을 바탕으로 다음 게임을 만들지, 현재 경험을 고칠지 결정한다. 이용이 거의 없다면 재미를 판정하기 전에 유입 경로부터 점검한다. 경험과 품질 기준은 [제품 기획서](product-brief-live-party-game.md)에 둔다.
